# NEXUS V1 需求边界与数据模型评审

> 文档用途：作为网页管理后台、Android 客户端和统一 Supabase 后端共同遵循的 V1 设计基线。
> 本文件只记录需求与建议，不会创建、修改或部署任何云端数据库，也不代表真实用户、订单或付款数据已经存在。

## 1. 当前仓库基线（2026-11-21）

- 默认分支：`main`；当前主线 Android 包版本为 `1.0.19`。
- 前端入口：根目录 `index.html`；Android 使用 Capacitor 打包同一套 Web 内容。
- 前端代码已经包含 Supabase 客户端初始化、邮箱注册/登录/重置密码，以及对 `profiles`、`plans`、`orders`、`subscriptions` 的读写调用。
- `sql/01_nexus_schema.sql` 已包含这些表、用户注册时创建资料的触发器、管理员检查函数、开通订阅函数和基础 RLS 策略。
- **代码里存在 Supabase 项目地址和 publishable key，不等于已经验证云端项目可用。** 当前仍需单独核实：项目是否正常、SQL 是否已执行、Auth 邮件设置是否正确、RLS 是否与前端行为一致。
- 当前提交订单界面明确提示“不进行在线扣款”。仓库没有可据此确认的真实支付流程；不得把订单申请称为已付款订单。
- 现有页面中的连接动画、地区/节点列表和协议偏好属于演示 UI，不是真实网络连接。本项目后续需求与开发范围不包含节点、代理线路、跨境 VPN 分发或规避监管功能，不得将这些演示控件接入真实网络服务。

## 2. V1 产品范围

### 必须支持

1. 用户邮箱注册、登录、退出和密码重置。
2. 用户查看及修改自己的基础资料。
3. 用户查看已上架的数字服务订阅套餐。
4. 用户提交订单申请，并查看自己的订单状态。
5. 管理员查看待处理订单，执行通过或拒绝。
6. 通过审核的订单按明确规则生成订阅；用户可查看订阅开始时间、到期时间和状态。
7. 管理员操作留下可追溯记录。
8. 网页管理后台与 Android 客户端共享同一 Supabase Auth 用户体系和数据库，不维护两套账户/订单数据。

### 暂不支持

- 在线扣款、自动续费、退款和银行卡/支付账户信息存储。
- 真实网络接入、VPN/代理节点、线路分发、连接配置或规避监管功能。
- 在客户端保存 Supabase service-role key、管理员密码或其他服务端秘密。
- 把本地演示数据、示例套餐或尚未核实的云端记录描述为真实业务数据。

涉及真实经营、支付、个人信息处理或网络接入服务时，必须先核实经营主体、适用资质、隐私告知、数据保护和当地法律要求，再决定是否上线相应功能。

## 3. 用户角色与权限

| 角色 | 可查看 | 可执行 |
|---|---|---|
| 未登录访客 | 已上架套餐、注册/登录页面 | 注册、登录、发起密码重置 |
| 普通用户 | 自己的资料、订单、订阅 | 修改自己的显示名称；创建待审核订单；在允许的状态下取消自己的订单 |
| 管理员 | 用户资料、全部订单、订阅和操作记录 | 管理套餐、审核订单、按审核结果开通/取消订阅、按规则停用账户 |

管理员身份只能由可信的项目所有者/服务端流程授予。任何普通用户都不能通过修改自己的资料、请求参数或前端页面把自己变成管理员。

## 4. 建议的数据模型

以下是目标模型，不表示这些字段已经全部存在于当前数据库。实施时应通过新的、可审查的 SQL migration 增量升级，避免直接覆盖已有数据。

### `profiles` — 用户资料

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `id` | uuid PK / FK | 对应 `auth.users.id` |
| `display_name` | text | 用户可自行修改的显示名称 |
| `account_status` | text | `active` / `suspended`，只能由管理员修改 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 最近更新时间 |

### `admin_users` — 管理员名单

- `user_id` 对应 `auth.users.id`，另有创建时间。
- 普通用户只能读取判断自己是否为管理员所需的最小信息；不得开放客户端插入、更新或删除。
- 首位管理员通过受控的 SQL Editor/服务端操作设置，不允许公开注册自动获得管理员权限。

### `plans` — 套餐目录

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 套餐 ID |
| `name` / `description` | text | 名称与说明 |
| `price_minor` | bigint nullable | 最小货币单位的价格；未定价时可为空，不用字符串参与计算 |
| `currency` | char(3) | ISO 4217 货币代码，例如 CNY |
| `duration_days` | integer | 服务期限天数，必须大于 0 |
| `is_active` | boolean | 是否对用户展示 |
| `sort_order` | integer | 展示顺序 |
| `created_at` / `updated_at` | timestamptz | 时间戳 |

价格展示可由数值和货币格式化生成。不要把 `“价格待定”` 这类展示文字当作金额数据，也不要在未接入支付前声称金额已经扣款。

### `orders` — 订单申请

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 订单 ID |
| `order_no` | text unique | 面向用户展示的订单编号 |
| `user_id` | uuid FK | 下单用户 |
| `plan_id` | uuid FK | 对应套餐 |
| `plan_name_snapshot` | text | 下单时套餐名称快照 |
| `duration_days_snapshot` | integer | 下单时套餐期限快照 |
| `amount_minor` / `currency` | bigint / char(3) | 下单时价格快照；不代表已付款 |
| `status` | text | `pending`、`approved`、`rejected`、`cancelled` |
| `reviewed_by` / `reviewed_at` | uuid / timestamptz | 审核人和审核时间 |
| `admin_note` | text | 管理员内部备注，用户不可读写 |
| `created_at` / `updated_at` | timestamptz | 时间戳 |

### `subscriptions` — 订阅权益

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 订阅 ID |
| `user_id` | uuid FK | 所属用户 |
| `plan_id` | uuid FK | 对应套餐 |
| `source_order_id` | uuid unique FK | 来源订单，避免同一订单重复开通 |
| `status` | text | `active`、`expired`、`cancelled` |
| `starts_at` / `ends_at` | timestamptz | 生效与到期时间 |
| `granted_by` | uuid FK | 执行开通的管理员/可信服务身份 |
| `created_at` / `updated_at` | timestamptz | 时间戳 |

到期判断必须同时考虑 `ends_at <= now()`，不能只依赖状态字段是否被定时任务改成 `expired`。

### `admin_audit_logs` — 管理操作审计

建议记录操作者、动作类型、目标记录类型/ID、发生时间和必要的非敏感变更摘要。禁止记录密码、访问令牌、密钥、支付凭证或完整个人敏感信息。

### 支付数据

V1 不建立可收集银行卡或支付凭证的表。将来只有在选定合规支付服务商、确认资质与退款/对账流程后，才另行设计支付交易记录；敏感支付数据由合规支付服务商处理。

## 5. 订单与订阅状态规则

订单状态：

`pending → approved` 或 `pending → rejected`；用户可在业务允许时将自己的 `pending` 订单取消为 `cancelled`。审核完成后不得由客户端任意改回待审核。

订阅状态：

- `active`：当前时间早于 `ends_at` 且未取消。
- `expired`：当前时间已达到或超过 `ends_at`。
- `cancelled`：按明确的管理员规则提前取消。

**通过订单审核与生成订阅必须在同一个受保护的数据库函数/事务中完成**：校验管理员身份、订单仍为 pending、订单未生成过订阅，再更新订单、生成唯一订阅并写入审计记录。不能让前端先把订单改为 approved，再由另一个按钮手动开通，否则会出现“订单已通过但用户没有订阅”或重复开通。

## 6. 当前 SQL 的安全与一致性待修项

对 `sql/01_nexus_schema.sql` 的静态审阅发现以下问题。这里只记录风险，不在本次文档 PR 中修改数据库：

1. **资料权限过宽**：当前授予 authenticated 对 `profiles` 整行 UPDATE，策略只限制行属于本人；用户可能修改本应由管理员控制的 `account_status`。应撤销整表更新权，只授予 `display_name` 等允许用户修改的列。
2. **订单创建可伪造字段**：当前订单 INSERT 策略只校验 `user_id = auth.uid()`，没有强制 `status = 'pending'`，也没有在数据库端从套餐读取价格。客户端可尝试提交自定义状态/金额。应改用创建订单 RPC，由数据库根据当前用户和有效套餐生成订单快照。
3. **订单审核与订阅开通分离**：当前前端直接把订单更新为 `approved`，而订阅由另一个 RPC 单独开通；两者不是一个事务。
4. **订阅可重复发放**：当前 `nexus_grant_subscription(p_user_id,p_plan_id)` 不关联已审核订单，也没有来源订单唯一约束；管理员重复点击可能生成多条订阅。
5. **缺少审计表**：当前没有统一记录谁审核了订单、谁开通/取消订阅以及何时操作。
6. **到期筛选不足**：当前前端只按 `status = 'active'` 查询订阅，没有同时筛选 `ends_at > now()`；过期但状态未更新的记录可能继续显示为有效。
7. **套餐管理权限尚不完整**：当前 schema 允许读取套餐，但没有一套清晰的管理员套餐增删改流程。

## 7. 必须落实的数据库安全规则

- 所有含用户数据的表启用 RLS；默认拒绝，逐项开放最小权限。
- 普通用户只能读取自己的订单、资料和订阅。
- 普通用户只能修改自己的显示名称，不能修改账户状态、管理员名单、订单审核字段或订阅权益。
- 普通用户只能创建待审核订单；价格、套餐快照和订单编号由数据库可信逻辑生成。
- 管理员审核、套餐管理和订阅发放走受保护 RPC/服务端操作，并写审计记录。
- Supabase publishable key 可用于客户端初始化；service-role/secret key 只能保存在受保护的服务端环境变量中，绝不能放进 HTML、Android 包或公开仓库。
- 管理员页面的“隐藏按钮”不构成权限控制；数据库 RLS 和函数内必须再次校验权限。

## 8. 实施顺序与验收

### 阶段 A：确认现状
- 在 Supabase 控制台确认项目状态、Auth 邮箱验证设置。
- 确认 `01_nexus_schema.sql` 是否已执行；检查真实表结构和 RLS，不以仓库里存在 SQL 文件作为部署证据。
- 使用测试普通用户和管理员账号，不使用真实客户数据。

### 阶段 B：数据库安全升级
- 新建独立 migration，不覆盖旧 SQL。
- 修正资料列权限、订单创建与审核 RPC、订阅来源唯一约束、到期判断和审计日志。
- 用普通用户、管理员、未登录三种身份逐条测试允许/拒绝的读写操作。

### 阶段 C：前端接入
- 网页管理后台和 Android 客户端复用同一套数据接口和状态规则。
- 移除前端直接更新订单审核状态的做法，改为调用受保护 RPC。
- 所有错误均显示中文提示；日志不得包含密码、token 或密钥。

### 阶段 D：上线前
- 完成隐私政策、用户协议、数据删除/导出流程和安全检查。
- 若要开展真实经营、支付或网络接入服务，先完成适用资质与法律审查。
- 通过测试后才允许导入真实用户或订单数据。

### V1 验收标准

- 普通用户 A 无法读取用户 B 的资料、订单或订阅。
- 普通用户不能把自己改成管理员，不能把自己的订单改为 approved。
- 管理员只能通过一次受保护操作审核订单并生成至多一条订阅。
- 订单被拒绝或取消不会生成订阅。
- 到期订阅不会继续显示为有效。
- 网页和 Android 对同一账户显示一致的套餐、订单和订阅状态。
- 测试环境未接入支付时，界面始终明确显示“订单申请/待审核”，不显示“已付款”。
